# 8.3.3 — `Notification` GObject payload

> **`docs/plans/1.0-summary.md` is not updated** for this sub-plan until it is done and archived.

**Status:** **🚫 WITHDRAWN** — no `libocrpc` code change. Review concluded a `payload` property adds nothing useful.

**Parent:** [`8.3-libocrpc-live-handles-and-signals.md`](8.3-libocrpc-live-handles-and-signals.md)

**Was supposed to depend on:** [`8.3.1`](8.3.1-live-handles-and-remote-refcount.md)

---

## Why this plan was withdrawn

**Original idea:** put a `GLib.Object payload` on `Notification` so a server could say “here is the new window.”

**Why it does not work as a library feature:**

- A `MetaWindow` cannot be sent on the socket as a nested bin object (not `Bin.Serializable`; domain types stay in gnome-shell-rpc).
- If `payload` is never on the wire, the client never sees it — only a handle number can cross the process boundary.
- That handle already has a home: existing **`Notification.id`** + **`object_type`**, same as ollmfilesd file-reference notifications.
- **`Connection.export()`** already lives in [`8.3.1`](8.3.1-live-handles-and-remote-refcount.md). The **caller** exports and sets **`id`** — not the RPC library inside `write()`.
- A `payload` property that is stripped or skipped on encode is in-process sugar at best; a local variable is enough.

**Conclusion:** no new field on `Notification`. No `bin_write_prop` skip. No tests for this plan.

---

## What gnome-shell-rpc does instead (caller responsibility)

**Server** — when a window is created:

```vala
connection.write(new OLLMrpc.Notification() {
    method = "Window.created",
    object_type = "Window",
    id = (int) connection.export(meta_window)
});
```

**Client** — unchanged:

```vala
client.notification.connect((notif) => {
    if (notif.method != "Window.created") {
        return;
    }
    var handle = (uint64) notif.id;
    // RPC-Live-Remote.ref, RPC-Live-Subscribe.signal, …
});
```

That is [`8.3.1`](8.3.1-live-handles-and-remote-refcount.md) + existing `Notification` reference fields. Subscribe push notifications stay in [`8.3.2`](8.3.2-subscribe-unsubscribe.md) (`id` + `message` for `notify::`, etc.).
