## Explainers (things that were unclear)

### Agent-skill-discovery — what it is

- ℹ️ Upstream skill that **inventories** whatever the host thinks is installed: Claude/Copilot skill dirs, MCP configs, plugins, repo-local agents.
- ℹ️ Exists mainly so **`agent-skill-orchestrator`** can “discover resources” before scoring/planning.
- ℹ️ On Agent Pi we already inject a skill catalog (`{skills_md}` / `SkillSet`). A second skill that re-scans `~/.claude/…` is mostly noise.
- 🔷 **🚫** Ship discovery as-is.
- 💩 If orchestrator needs a Step 0: one short “use the catalog already in context” line — not a full discovery skill.

### Grill-me — what it is

- ℹ️ Soft skill: user says “grill me”; model asks **one** hard question at a time about a plan/design, with a recommended answer, until branches are exhausted.
- 🔷 **🚫** Skip for base pack (doesn’t fit).

### Skill-creator — concept vs Python

- ℹ️ **Concept (interesting):** interview the user → write a valid `SKILL.md` (name, pushy `description`, workflow, examples) → optionally try a few realistic prompts and improve the skill. Progressive disclosure (`references/` when fat). Authoring playbook for *making* skills.
- ℹ️ **Python baggage (skip):** `evals/`, `run_eval.py` (`claude -p` trigger tests), benchmark aggregation, HTML viewer — Claude Code QA harness, not Agent Pi runtime.
- 🔷 **🚫** Don’t vendor the Python/eval harness into the app.
- 💩 Optional later: ship **markdown-only** authoring guidance (strip scripts/evals) if we want users to create skills inside OLLMchat — confirm first; not v1.

### Git hygiene — what it meant

- ℹ️ LLM suggestions like getsentry `commit` / `create-branch` / `iterate-pr` — teach the *model* to run git via tools.
- 🔷 **🚫** Initial pack — git/file-change monitoring stays host/user responsibility; not an LLM soft-skill job for v1.

### Subagent-delegate — research status

- 🔷 Want a soft skill for delegating work to a sub-agent.
- ℹ️ Hunt so far: most “subagent” skills are **Claude Task / Agent tool** how-tos (`create-subagent`, obra `subagent-driven-development`, OpenClaw team orchestration) — harness-bound, not portable Agent Pi.
- 💩 `⏳` Keep hunting for a markdown playbook we can retarget to **our** sub-agent API (when/if we expose one); until then **omit** from vendored pack or human-port a thin brief.
- ℹ️ OpenClaw `agent-team-orchestration` is closer to multi-agent lifecycle than solo coding — possible reference, not locked.

### Research codebase

- 🔷 **Not** `deep-research`. That skill is **web** (browser). This one is **codebase**.
- 🔷 Default target: the **active / opened project** — whatever is indexed for **`codebase_search`** (semantic vectors), then drill with `read` / `bash` (grep, etc.).
- 🔷 “Another codebase” still means **local**: open/index that tree as the project (or path-scope search once we have it). **🚫** Do not pretend web search is codebase research.
- 🔷 Skill teaches **when/how** to explore: start semantic (`codebase_search`), then precise read/grep; summarize findings for the user / next skill.
- ℹ️ Upstream soft playbooks (seb1n / Trail of Bits explore-style) are optional **structure** only — retarget tools to ours; do not ship web-research wording.
- 💩 Exact skill name / whether we human-port a thin `SKILL.md` vs adapt an upstream tree — lock when vendoring (still no LLM-invented full bodies if we can avoid it; thin port OK if no good upstream).

### Debug / review

- 🔷 Two jobs often confused:
  - **Debug** (broken behaviour) — our **`docs/bug-fix-process.md`**: reproduce → `docs/bugs/` log → evidence → root cause → propose (fences) → **approval** → apply. Never hide with defensive guards.
  - **Review** (diff / PR quality) — getsentry-style checklists: security, perf, tests, design on **changed** code.
- 🔷 Want **one** soft skill (working name `debug-review`) that **mixes** them:
  - Spine = **our** debug standards (emoji bug logs, no symptom-only patches, approval before apply).
  - Borrow **review checklist** ideas from getsentry `find-bugs` / `code-review` (attack surface, severity, evidence) — strip Sentry/Django-only noise.
- 🔷 🚫 Do **not** ship getsentry skills unchanged (git-diff-only find-bugs ≠ our debug process; their code-review is PR critique, not bug-fix workflow).
- ℹ️ Candidates to skim for checklist language only:
  - [getsentry find-bugs](https://github.com/getsentry/skills/tree/main/plugins/sentry-skills/skills/find-bugs)
  - [getsentry code-review](https://github.com/getsentry/skills/tree/main/plugins/sentry-skills/skills/code-review)
- 💩 Whether split into two skills later (`debug` vs `code-review`) if the mix feels muddy — confirm after first draft shape.
- 🔷 `⏳` Draft approach: **references/** (or short sections) pointing at / paraphrasing project bug-fix rules + a compact review checklist; Agent Pi tools only.
